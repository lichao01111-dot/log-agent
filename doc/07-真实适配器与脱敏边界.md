# 第七课：真实适配器与脱敏边界

> 本课是真实接入前的设计与验收门槛，不是“Splunk MCP 和真实 LLM 已经接通”的实现记录。本章所有外部字段名、tool 名和调用流程都必须以将来获取的真实 Schema 为准，不在文档中猜测。

## 这一课解决什么问题

前六课已经把两个应用内边界稳定下来：

- `LogSearchPort` 只接收经过策略门的 `AuthorizedQueryPlan`；
- `StructuredModelClient` 只接收有界上下文，并只返回结构化草稿。

但“应用内类型安全”不等于“外部调用已安全”。中间还缺三层：

```mermaid
flowchart LR
    A["AuthorizedQueryPlan\n应用内已授权计划"] --> R["Wire Renderer\n固定模板 + 字面量编码"]
    R --> S["Splunk MCP Adapter\n作业生命周期 + 传输预算"]
    S --> N["Normalizer + Redactor\n最小化事实"]
    N --> P["SearchResult\n应用自有结果"]
    P --> M["StructuredReasoningAdapter"]
    M --> C["StructuredModelClient\n真实 Provider Adapter"]
```

这三层不能靠一个 `pip install` 补齐。它们分别解决查询渲染、远程资源失控和生产数据外发风险。

## 为什么真实接入现在仍然阻塞

截至当前仓库状态，仓库没有提供 Splunk MCP 的真实 Schema、服务端能力清单或可调用 Adapter。因此下列信息都还不是已知事实：

- 真实 tool 名、服务版本和请求/响应 Schema；
- 是否支持 oneshot，还是必须 dispatch job 再 poll；
- 时间参数、时区、边界包含关系和最大时间窗；
- 分页方式、稳定顺序、总命中数和截断语义；
- job 终态、轮询建议、超时、取消和服务端 TTL；
- 错误码、限流、重试、认证和 RBAC 保证；
- 行级稳定定位符是否存在，以及什么可以成为 `record_ref`。

另一个独立阻塞是数据外发。当前 `SearchResult` 可以限制数量和文本长度，第六课也要求 `ReasoningTextSanitizer`，但测试替身不是生产脱敏器。在字段分类、凭据/PII 规则、允许外发清单、原文存储和访问审计未验收前，不能把真实生产日志发送给外部模型。

## 第一道门：Splunk MCP Contract Inventory

实现 Adapter 之前，先把真实 MCP 当成一个未知的外部协议。使用工具自省、官方 Schema 或服务端管理员提供的契约，产出一份可评审的 inventory。

| 类别 | 必须确认的事实 | 不接受的猜测 |
|---|---|---|
| 能力发现 | server/tool 精确标识、版本、Schema | 根据其他 Splunk SDK 猜 tool 名 |
| 查询输入 | 可执行语言或结构化参数、时间、limit | 假定字段名一定是 `query` 或 `earliest` |
| 执行模式 | oneshot/job，job handle 形式，状态集合 | 把 SDK 中的 sid 当作 MCP 必然返回值 |
| 结果 | row Schema、字段类型、编码、空值 | 把任意响应当成 `list[dict]` |
| 分页 | cursor/offset/其他方式、顺序稳定性 | 用本地行号假装稳定记录 ID |
| 完整性 | total、has-more、truncation 的定义 | 返回数量小于 limit 就宣称完整 |
| 生命周期 | poll 建议、终态、cancel/cleanup、TTL | 调用方自创一套远程状态 |
| 故障 | 错误码、限流、超时、可重试语义 | 直接向上抛服务端原始异常 |
| 安全 | 身份来源、凭据范围、只读 RBAC、审计 | 把本地 allowlist 当成服务端授权 |
| 资源限制 | 请求字节、响应字节、job 数、频率 | 只限制 `SearchResult` 行数 |

inventory 必须保存 Schema 快照或经过脱敏的 fixture，记录获取日期与服务版本。契约升级时先跑契约测试，而不是在生产调用失败后才发现字段变了。

只要这份 inventory 没有完成，仓库就不应该出现一个自称“真实”的 Splunk Adapter。

## 第二道门：从 AuthorizedQueryPlan 到 Wire Renderer

`AuthorizedQueryPlan` 是应用进程中由 `QueryPolicyGate` 密封构造的非执行计划。它包含：

- 精确 `scope_ref`；
- 策略允许的 `(index, sourcetype)` 配对；
- 版本化 `template_id`、`QueryOperation` 和 `QueryKind`；
- 已约束的时间范围、返回上限和 `QueryLiteral`。

它不是 SPL，也不是可以在网络上转发的授权令牌。Renderer 必须位于受信 Adapter 内部，并且只能做如下映射：

```text
template_id + operation
→ 选择代码内受评审的固定模板

sources + time_range + result_limit
→ 按真实 MCP Schema 填入受信参数

literal_terms
→ 通过专用字面量编码器作为数据填入
```

这条边界有七条硬规则：

1. Renderer 按 `template_id` 正向选择完整模板，没有通用“补一段 SPL”接口。
2. 未知 template/operation 直接拒绝，不 fallback 到默认查询。
3. source 只来自 `AuthorizedQueryPlan.sources`，模板文字、模型输出和 MCP 回显都不能添加 source。
4. `QueryLiteral` 虽然已经通过窄字符集，Renderer 仍必须按真实语法编码，不能直接字符串拼接。
5. 时间和 limit 必须使用契约确认的精确语义，不能用库默认值静默修改计划。
6. 渲染后再做一次最终结构验证：数据源、时间、limit、模板版本和只读操作都必须与计划一致。
7. 若未来 Adapter 拆到另一进程，接收端必须重新解析并授权，不得盲信反序列化的 `AuthorizedQueryPlan`。

若真实 MCP 接受结构化查询而不是 raw SPL，Renderer 仍然有价值：它渲染的是受控 wire arguments，而不是查询字符串。在 contract inventory 完成前，本课不提供任何假定的 SPL 或 wire 字段示例。

## 第三道门：远程查询生命周期和传输预算

### Oneshot 与 Job 不能先选后验

oneshot 只在真实契约同时保证“可限制结果、可限制响应字节、可观测截断、超时/取消语义可控”时才可以使用。任一项不满足，就应使用有界 job 流程，或者直接判定当前 MCP 不适合生产接入。

job 流程的逻辑状态是：

```text
dispatch
→ poll（有界）
→ fetch page（有界）
→ normalize
→ cancel/cleanup（必要时）
```

这不是 Agent 状态机的新阶段，而是 `LogSearchPort.search()` 内部的 Adapter 生命周期。领域层仍然只看到一次逻辑查询成功或失败。

### 逻辑预算与传输预算不是一件事

状态机的查询预算在发出 `ExecuteQuery` 时消耗，用来限制 Agent 能发起多少次逻辑查询。一次逻辑查询之内可能还有很多远程操作，它们必须另外受限：

| 传输预算 | 防止的失控 |
|---|---|
| 总 wall-clock deadline | job 永不终止 |
| 最大 poll 次数 | 高频空轮询 |
| poll 最小/最大间隔 | 压垮服务或拖延取消 |
| 最大 page 数 | 分页无限遍历 |
| 单页/总行数 | 规范化对象过多 |
| 单页/总响应字节 | 在解析前耗尽内存 |
| 最大连续故障和重试数 | 网络故障放大 |
| 最大并发 job 数 | 同时占满 Splunk 资源 |

这些预算中任意一项被触发，Adapter 都必须停止继续收集。如果是在页边界达到 page/总行数/总字节上限，已收集页面完整、结构合法，且当前 operation 明确允许样本结果，可以返回 `truncated=True` 的部分 `SearchResult`。如果是 poll/deadline/单个响应字节/解析故障，无法得到完整合法的返回单元，则必须尝试有界 cleanup 并返回已清洗的 `PortError`。不能把远程超时伪装成“零结果”或“未找到根因”。

poll、page 和同一 job 的安全传输重试不会再次消耗领域查询预算，但它们会消耗传输预算。对 dispatch 的模糊失败不能盲目重发：远程可能已经创建 job。只有契约确认幂等键或能通过 `operation_id` 可靠查回时，才能安全重试 dispatch。

### 取消的正确语义

- Python task 取消必须最终原样传播 `CancelledError`；
- 若契约支持 remote cancel，Adapter 可做一次有界的 best-effort cleanup，但不能因 cleanup 卡住取消；
- 若契约不支持 cancel，Adapter 必须停止 poll，并把远程 TTL 和资源风险列入接入评估；
- 用户主动取消调查应由第 9 章待实现的上层控制通道可靠地转换为 `CancelRequested`；当前 Runner 尚未提供这条通道，不能用一个被吞掉的 task cancellation 冒充已经完成。

## 第四道门：SearchResult 规范化和生产脱敏

外部返回的任意对象都是未可信输入。Adapter 必须在接收和解析时强制字节、嵌套深度、行数和字段数上限；不能将一个已被拦腰截断的结构伪装成合法响应。只有通过精确契约解析的完整行或完整页，才能参与构造 `SearchResult`。

```text
MCP response
→ 传输字节上限
→ 严格 Schema 解析
→ 物理字段 allowlist / 分类
→ 凭据、PII 和高基数标识符 Redactor
→ 最小化 Fact / summary
→ 本地 EvidenceRef
→ SearchResult
```

### `SearchResult` 的现有语义不能被 Adapter 改写

- `result_count` 是返回给应用的规范化行数，不是 Splunk 总命中数；
- `evidence` 数量和 `facts` 数量都不能超过 `result_count`；
- Fact 只能引用本次结果中已构造的 Evidence ID；
- Evidence 的 `query_id` 必须等于请求的 `query_id`，Executor 会再校验一次；
- `record_ref` 是本地不透明引用，不是原日志、带凭据 URL 或模型可见字段；
- 无法证明完整时，`truncated` 必须为 `True`，不能乐观猜测为 `False`。

若后端未提供稳定行 ID，不能把“当前第 7 行”写成可跨时间使用的 `record_ref`。可选方案是将经过访问控制的证据快照留在本地 evidence store，`record_ref` 只指向该快照；这个存储合同、保留期和权限尚未设计。

### Normalized 不等于 Sanitized

规范化只是把外部形状转成内部形状。一条格式正确的 Fact 仍可能含有 access token、cookie、邮箱、手机号、订单号、payload 或 prompt injection 文字。

生产 Redactor/Sanitizer 至少需要：

- 物理字段默认不可外发，只有已分类的 allowlist 字段可进入 Fact；
- 在拼接 summary 和 Fact 之前脱敏，不能先构造一段可能泄密的大文本；
- 区分删除、不可逆令牌化和仅调查内稳定的代用符；
- 对未知字段、未能安全解析的文本和策略版本不匹配 fail closed；
- 错误、trace、调试输出和模型请求记录走同样的敏感数据策略；
- 用 canary 凭据、带签名 URL、结构化 PII 和 prompt-injection 文本做负向测试。

第六课的 `ReasoningTextSanitizer` 是“任何动态文本离开进程前必须过的端口”。未来生产实现不能只做几个正则替换；它必须与物理字段分类、scope、保留期和外发政策绑定。如果策略不能确认一段文本可外发，它应该抛出已清洗的 `ReasoningTextSanitizationError`，而不是返回原文。

## 第五道门：真实 StructuredModelClient Provider

真实 provider Adapter 只能实现现有 `StructuredModelClient.generate()` 契约，不得把 provider SDK 泄漏到状态机、Executor 或 `StructuredReasoningAdapter`。

| 边界 | Provider Adapter 必须保证 |
|---|---|
| 模型可见数据 | 只发送 `instructions`、`input_json` 和 `response_schema_json` |
| 本地 trace | `trace_context` 不得进入 prompt、provider metadata、tool arguments 或任何外发字段 |
| 输出形式 | 请求结构化 JSON，统一映射返回文本、refusal 和 finish reason |
| token 上限 | 在真实生成请求中应用 `max_output_tokens` |
| 字节上限 | 流式接收时边读边计数，超过 `max_output_bytes` 就停止，不能完整缓冲后才检查 |
| 工具调用 | 该端口不需要工具；意外 tool call 映射为非完整输出 |
| 错误 | 预期 provider 故障转为已清洗 `PortError` / `PortUnavailable` |
| 取消 | 立即停止读取/发送，最终原样传播 `CancelledError` |
| 未知缺陷 | 编程错误原样暴露给测试和内部监控，不伪装成普通诊断失败 |

`PortError.safe_message` 不得包含用户问题、日志片段、响应体、凭据、请求 URL 或 provider 回显的原文。provider 的 request ID、限流细节和调试信息若需内部记录，也必须先通过单独的观测性数据分类，不能塞进对用户可见的安全消息。

Executor 现在会为整次 reasoning 调用设置外层超时。Provider Adapter 的连接、首字节和流式读取 deadline 必须不超过剩余外层 deadline。传输重试与 `repair_attempt` 也必须分开：前者是有界网络策略，后者是第六课对无效结构化草稿最多一次的修复。

## 契约测试矩阵

真实 Adapter 不应靠一次手工调用验收。下表是接入前的最小契约矩阵：

| 层 | 正向用例 | 负向/边界用例 | 关键断言 |
|---|---|---|---|
| Contract inventory | 当前 Schema fixture 可解析 | 缺字段、多字段、版本变更 | 契约漂移 fail closed |
| Renderer | 两个已授权 template 的 golden output | 未知 template、伪造 source、恶意 literal | 无数据源扩张、无语法逃逸 |
| Oneshot | 完整有界响应 | 过大响应、超时、完整性未知 | 预算触发就停止，不返回假完整结果 |
| Job/poll | 正常达到终态 | 未知状态、poll 耗尽、job 失败 | 有界终止并清洗错误 |
| Pagination | 多页稳定合并 | cursor 循环、重复页、页数/字节超限 | 去重规则明确，截断不被隐藏 |
| Cancel | 远程 cleanup 成功 | cleanup 失败或超时 | `CancelledError` 仍原样传播 |
| Error mapping | 已知限流/不可用 | 原始异常含凭据或日志 | 只出现固定 code 和 safe message |
| Normalization | 合法 row 变成 Fact/Evidence | 错类型、重复 ID、跨 query 引用 | `SearchResult` 和 Executor 双重校验 |
| Completeness | 已证明完整 | 服务截断、本地 page/byte/deadline 截断 | 任一不完整来源都使 `truncated=True` |
| Redaction | 允许字段通过 | token/cookie/签名 URL/PII/canary | 禁止内容不进入 Fact、prompt、error 或 trace |
| Provider request | 三段数据精确映射 | trace canary、意外 metadata/tool | `trace_context` 零外发 |
| Provider stream | 正常 JSON 结束 | token/byte/deadline 超限、中途取消 | 缓冲前边读边限制 |
| Provider result | stop + JSON | refusal、length、content filter、tool call | 映射到现有 envelope，交给结构化 Adapter 处理 |
| Staging RBAC | 允许的 source 可读 | 未允许 source、写操作 | 服务账号从服务端拒绝 |

Renderer、job 生命周期和规范化测试应先对脱敏 fixture 执行；只有 staging RBAC 和服务端语义验收需要受控真实环境。生产凭据不应出现在 fixture、测试失败快照或 CI 日志中。

## 接入顺序与完成门槛

真实接入建议严格按以下顺序：

1. 获取真实 MCP Schema 和服务端能力，完成 contract inventory。
2. 冻结经脱敏的正向、失败、分页和截断 fixture。
3. 实现固定模板 Renderer，完成对抗性 golden tests。
4. 实现有界 transport 和 oneshot/job Adapter，完成取消、超时、分页和错误契约。
5. 实现最小化 Normalizer 和本地 evidence reference 策略。
6. 由系统负责人和安全负责人批准字段分类、Redactor 与原文访问策略。
7. 用脱敏数据实现并评估一个真实 StructuredModelClient Provider Adapter。
8. 在受控 staging 验证只读 RBAC、资源上限、脱敏和端到端取消。

满足下列条件前，不得宣称“真实生产链路已打通”：

- 所有外部字段和状态都可追溯到真实契约；
- Renderer 无 raw 语法注入口，并通过对抗性测试；
- page、poll、bytes、deadline、concurrency 和 retry 预算都可测；
- 无法证明完整的结果不会被标记为完整；
- 生产 Redactor 通过 canary 和字段分类测试；
- `trace_context`、`record_ref`、原始日志和原始错误在 provider 请求中为零；
- 只读 RBAC 在服务端经过负向验收；
- task cancellation 与用户取消都有明确、不泄漏资源的路径。

## 本课已有与未完成的边界

仓库已有：

- SPL-free 的 `QueryPlan` 和密封 `AuthorizedQueryPlan`；
- 精确 scope、source pair、template/operation、时间和 result limit 策略门；
- provider-neutral `LogSearchPort` / `SearchRequest` / `SearchResult`；
- Executor 的外层超时、协议校验、`PortError` 翻译和 cancellation 传播；
- provider-neutral `StructuredModelClient`，以及结构化草稿、证据别名和本地输出上限；
- Fake Log Search 和 Fake Structured Model 的无网络端到端回归。

仓库还没有：

- 已确认的 Splunk MCP contract inventory；
- 任何真实 Splunk tool 调用、Wire Renderer 或 job/poll/page/cancel 实现；
- 真实 MCP 响应 fixture 和契约漂移检测；
- 生产物理字段策略、Normalizer、Redactor 和 evidence store；
- 任何真实 LLM Provider Adapter；
- 真实日志与真实模型的质量、成本和延迟评估。

因此本课的准确成果是：**我们定义了真实适配器可以开始实现的条件、不能跨过的数据边界和完成验收标准；真实外部接入本身仍未完成。**

## 动手练习

### 练习 7.1：只做契约盘点

在能访问真实 Splunk MCP 的环境中，仅完成 contract inventory，不执行生产查询。保存 Schema 快照，并回答：

- 是 oneshot 还是 job？
- 哪些字段是必填，哪些有默认值？
- 如何证明结果完整？
- 是否能取消？取消后远程资源何时释放？
- 服务账号如何在服务端被限制为只读？

若任一答案不能从契约或服务端验收中获得，把它写成 blocker，不用推测填空。

### 练习 7.2：Renderer 对抗性设计

不连接外部服务，先根据已获得的 Schema 写 Renderer golden tests。构造这些输入：

- 两个已允许 source pair；
- 一个未知 template ID；
- 一个包含管道、子查询、换行或引号的候选 literal；
- 一个试图把 limit 扩大的伪造计划。

期望的不只是“查询可执行”，还包括渲染后 source、时间、limit 和操作与授权计划精确一致。

### 练习 7.3：有界 Job Fake

用一个只模拟真实 Schema 的 transport Fake 分别演练：

1. 两次 poll 后完成，返回两页；
2. cursor 重复导致分页循环；
3. poll 一直不达终态；
4. 第二页前 task 被取消；
5. dispatch 返回前断线，无法判断 job 是否已创建。

为每条路径写出它消耗的逻辑查询次数、poll/page/byte 预算、cleanup 行为和最终应用事件。

### 练习 7.4：脱敏 Canary

构造一个包含以下内容的脱敏 fixture：伪 token、cookie、签名 URL、邮箱、订单号、未知 JSON 字段和“忽略之前指令”文本。断言敏感 canary 和未知字段的原值不出现在：

- `SearchResult.summary` 和 Fact；
- `StructuredModelRequest.input_json`；
- `PortError.safe_message`；
- trace 和测试失败输出。

另外断言 prompt-injection 文本永远不出现在受信 `instructions`，也不会直接触发查询或状态转移。它是否在 `input_json` 中以未可信、已最小化的数据保留，由已审批的外发策略决定；它不一定需要像凭据一样全部删除。

### 练习 7.5：Provider 流式预算

用 Fake stream 生成一个语法最终合法、但接收中途已超过 `max_output_bytes` 的 JSON。真实 Provider Adapter 必须在流式读取时停止，而不是把完整输出放入内存后再依赖第六课的本地解析上限。再加一个 trace canary，证明 `trace_context` 没有进入任何 provider 外发字段。

## 你应该记住什么

```text
本地类型通过 ≠ 远程契约已确认
查询逻辑预算 ≠ poll/page/byte 传输预算
Normalized ≠ Sanitized
有 trace 可观测性 ≠ trace 可外发
Fake 端到端通过 ≠ 生产链路已打通
```

真实 Adapter 的价值不是“把一个 SDK 调通”，而是把一个不受我们控制的外部协议，转换成可验证、可截断、可取消、不泄漏的应用能力。
