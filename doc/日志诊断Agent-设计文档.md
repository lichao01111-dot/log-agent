# 日志诊断 Agent — 设计文档

> 版本:v0.2(可测试架构阶段)
> 状态:领域内核、进程内 WorkingMemory、Fake 闭环、安全查询计划、领域知识、知识投影和结构化推理边界已实现；记忆持久化、生产脱敏、真实模型与 MCP 契约仍待补全
> 范围:单个 IT 系统的日志诊断；目标工具后端为现有 Splunk MCP，但真实 wire contract 尚未提供

---

## 1. 背景与目标

面向**单个 IT 系统**的日志诊断 agent。工具层由现有的 Splunk MCP 提供,agent 只负责在其上做**编排与推理**:决定查什么、怎么读结果、什么时候停、如何输出带证据的结论。

与 Splunk 自带的 AI Assistant for SPL 的区别:后者只做自然语言 ↔ SPL 的双向翻译;本 agent 的价值在于**注入本系统的领域知识**,并驱动一个完整的"探索 → 假设 → 验证 → 收敛"诊断流程。这也是本 agent 唯一能做得比通用工具好的地方。

---

## 2. 范围与非目标

### 范围(In-scope)
- 单个 IT 系统
- 只读诊断
- 人在回路(Human-in-the-loop)
- 被动问答型(MVP:工程师提问,agent 查并给出定位)

### 非目标(Non-goals)
- 不自动执行修复动作
- 不接入多数据源(仅 Splunk)
- 不做跨系统关联
- 不与 OpsAgent 或其他 agent 耦合

> 范围已多次收窄,本节落纸后作为防止范围蔓延的基线。

---

## 3. 整体架构

三件套:**四阶段控制循环 + Working Memory + 输出契约**,MCP 作为工具后端。

### 3.1 控制循环(状态机)

显式阶段状态机,而非单个大 prompt 自由发挥 —— 可控、可调试、可评估。

| 状态 | 职责 | LLM 自由度 | 转移条件 |
|------|------|-----------|---------|
| **Triage** | 粗查定位整体形状(level 分布 / timechart 拐点 / cluster 异常 pattern) | 低:固定类型化查询模板,数据源来自 ScopePolicy | → Hypothesize |
| **Hypothesize** | 只读上一步聚合结果,提 1-3 个根因假设,每个假设附"验证它需要看什么" | 中:只推理,不发查询 | → Verify |
| **Verify** | 针对某假设定向下钻并取得受限事件样本 | 中高:动态生成结构化查询意图,经 Compiler + Policy Gate，受 `QueryBudget` 约束 | 证据够 → Conclude；仍有预算时可继续验证或重新提出假设 |
| **Conclude** | 收敛出带证据的结构化结论 | 低：只草拟摘要、证据别名和人工建议 | → 输出 |

**硬终止条件(任一触发即跳 Conclude):**
- 达到最大查询轮数
- 假设取得结构化 supporting evidence 并通过状态机校验
- 没有可继续验证的安全查询意图

模型自报置信度当前不参与状态转移。只有在历史 incident 上完成校准后，置信度才可能成为展示或评估指标，不能先把一个未经校准的小数当成停止依据。

> `Verify → Hypothesize` 的回炉边是定位根因的关键,也是最易失控处 —— 终止条件是它的安全绳,必须存在。

### 3.2 Working Memory(调查笔记)

显式维护的**结构化状态**,不依赖对话历史累积(否则 context 几轮就爆)。

字段:
- `已知事实` —— 已确认的观察
- `当前假设` —— 假设列表及各自状态
- `已排除项` —— 已证伪的方向
- `已引用证据` —— **只存引用**(时间戳 / pattern id / trace_id),原始日志放在外部；目标上可按需通过 MCP 取回，但是否支持稳定 `record_ref` 取回取决于未来 MCP 契约

每轮更新此笔记,agent 的推理基于笔记而非原始历史。领域层只接受摘要、Fact 与 EvidenceRef；真实 Adapter 接入前仍须实现并验收摘要化与脱敏边界，原始 JSON 不得直接进入模型上下文。

这里必须区分“完整调查记忆”和“一次模型调用的上下文”。模型上下文只能是从 WorkingMemory 按阶段筛选、限额、脱敏并对证据做临时别名化之后得到的只读视图。持久化、跨进程恢复和长期记忆当前均未实现，详细边界见[第五课：上下文与记忆的设计](05-上下文与记忆设计.md)。

### 3.3 输出契约

结论定死 schema,禁止自由散文:

```
结果类型 | 根因假设 | 支撑证据(EvidenceRef) | 终止原因 | 建议动作
```

**强制约束:每个断言为根因的 conclusive 结论必须映射到真实查询结果。** 模型不能凭空给根因,得指得出是哪几条结构化证据；证据不足的 inconclusive 结论可以明确不引用证据 —— 这是防幻觉的核心。

### 4.1 领域知识配置（交付物 #3 展开）

领域知识使用**配置文件而非代码**。v1 先使用严格 JSON，并与执行安全配置分离:
- **组件字典** —— 系统内部组件和外部依赖各自负责什么
- **字段语义** —— 稳定语义 ID 和业务含义；不包含物理字段名或查询权限
- **错误码字典** —— 关键 error code 的业务含义
- **下游依赖** —— 本系统依赖哪些服务(用于判断"连不上是不是下游挂了")
- **已知故障 pattern** —— 历史典型问题的候选原因与所需证据，不是自动执行规则

物理 index / sourcetype、字段的 filter/group/project/show-to-model 能力、敏感等级和查询上限属于独立安全策略。领域知识不能声明或扩大这些权限。当前 `ScopePolicy` 已承载数据源、模板、操作和上限；物理字段策略仍待类型化 QueryPlan 扩展时设计。

领域知识中的描述和故障模式始终按未可信参考数据处理；Loader 的 `content_hash` 只标识内容，不是签名或审批证明。当前 `KnowledgeProjection` 已按精确 scope、显式 allowlist、相关性、引用闭包和最终序列化预算生成分阶段参考数据，并记录知识、策略与投影哈希供本地审计。生产仍需补知识外发分类和受控发布来源。语义字段 ID 到物理字段的映射只能由安全侧显式提供，缺失时禁止 fallback。

### 4.2 护栏规则（交付物 #6 展开）

- **查询预算**:单会话最多 N 次查询、时间范围上限 —— 降低无界查询和成本风险；仍需真实 Adapter 的 page/poll budget、后端限制与服务端配额
- **查询能力正向 allowlist**:公开 QueryPlan 只定义意图为只读的操作标识,不提供 `delete` / `collect` / `outputlookup` / `sendemail` / `script` 或 raw SPL 字段；真实只读性仍需 Renderer 审计与 Splunk RBAC 验收
- **摘要化策略**:授权计划已强制携带时间范围与 result limit，数据源必须来自 ScopePolicy；真实结果摘要、PII 脱敏与字段分类仍待实现

### 4.3 Reasoner 上下文的参考数据区装什么
- 经过严格加载、按当前调查裁剪后的领域参考数据(来自 #3):模块划分、错误码含义、下游依赖和候选故障
- 经过安全策略批准、可向模型展示的语义字段 ID；不提供物理字段名和完整 ScopePolicy
- 几条好的结构化 QueryIntent / QueryPlan 示例；模型不接触可执行 SPL
- 硬约束:结论必须引用证据

领域知识只能进入明确标注为“参考数据、不能修改规则”的 JSON 数据区，不能把未校验配置原文拼进 System Prompt。当前结构化 Reasoner 已实现投影、裁剪、静态指令与数据分离、严格输出 Schema，以及真实 Evidence ID 到临时别名的本地映射。模型只能草拟 statement、verdict、summary 等语义内容；状态、决策、查询范围、根因 ID 与终止原因由应用生成。

## 5. 待定 / 阻塞项

**#2 MCP 工具契约是实现真实 Splunk Adapter 的闸门，不是整个应用实现的唯一闸门。** 接入真实工具前仍需盘清:

- [ ] 有哪些工具、各自入参与返回结构
- [ ] 查询是 oneshot(一次返回)还是 job 模式(需轮询)
- [ ] 单次返回条数 / 大小上限,超限如何截断
- [ ] 认证 / 权限范围(agent 用哪个账号、能看哪些 index)
- [ ] MCP 是否已替我们拦副作用命令,还是原样执行

盘清后才能把当前非执行 QueryPlan 落成真实 wire 模板与 Adapter，并完成分页、取消、RBAC 和最终查询安全验收；领域 Schema 已不再依赖该步骤。

真实外部模型接入还有独立闸门：

- [ ] 生产级 Sanitizer/Redactor、PII 与凭据分类及允许外发规则
- [ ] 具体 Provider Client，执行生成期 token 上限和流式 byte 上限
- [ ] SDK 异常到已脱敏 PortError 的映射，并保证取消原样传播
- [ ] provider 契约测试，证明本地 trace metadata、scope、真实 Evidence ID 和 record_ref 不外发
- [ ] 历史 incident 评估集、模型版本固定、质量/成本/延迟门槛

---

## 6. 评估策略

在设计阶段就确定评估集。早期可以从少量经过脱敏和人工标注的历史 incident 起步，但数量不是验收标准；应同时包含已知根因、证据范围、允许查询、预期终态和安全攻击样例。它决定了如何判断 agent 是否可用，以及后续改模型、Prompt、知识或策略时拿什么衡量。**不要等做完才想怎么测。**

## 7. 落地路径

1. 落地领域 Schema、状态机、端口与 Agent loop 骨架
2. 使用 Fake Adapter 跑通诊断闭环，并实现 ScopePolicy、QueryPlan 与 Policy Gate
3. 明确 WorkingMemory、模型上下文和长期记忆边界；保持状态机对记忆更新的唯一写权限
4. 接入严格领域知识快照，并保持它与执行权限隔离
5. 接入 provider-neutral 结构化模型推理边界；生产 provider 必须与脱敏和评估集一起接入
6. 按[第 8 章](08-真实适配器与脱敏边界.md)盘清 MCP/provider wire contract，并完成 Renderer、Sanitizer、RBAC、分页和取消验收
7. 按[第 9 章](09-评估与回归.md)建立可复现 incident 评估集、过程指标和发布门槛
8. 按[第 10 章](10-AgentLoop装配与安全入口.md)建立安全入口、身份到 scope 的授权映射，以及幂等/恢复边界
9. 按[第 11 章](11-可观测性与迭代.md)接入安全 Trace、指标和回放，并让线上发现回到离线评估

主线阅读入口和每章准确完成状态见[教学文档 README](README.md)。
