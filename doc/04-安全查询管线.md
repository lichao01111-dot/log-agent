# 第四课：安全查询管线

## 先看失败案例

假设模型或用户提供：

```text
scope_ref = "checkout-prod | index=secret"
goal = "index=* | delete"
```

如果应用把这两个字符串直接拼成 SPL，再在末尾追加 `| head 100`，结果限制并不能阻止前面的越权查询或副作用命令。扫描 `delete` 等关键词也不可靠：它可能误伤普通日志文本，也可能被宏、子搜索或语法变化绕过。

所以本项目使用正向允许：公开查询模型中根本没有 raw SPL，也没有 `DELETE`、`COLLECT`、`OUTPUTLOOKUP` 等操作。

> 本课只完成应用进程内的查询计划约束。`AuthorizedQueryPlan` 不是用户授权令牌，也不证明未来 SPL 安全、MCP 会遵守限制或 Splunk RBAC 配置正确。只有真实 Renderer、Adapter 契约测试和服务端最小权限全部验收后，才能讨论端到端查询安全。

从 `SafeQueryPipeline.prepare()` 反向展开最容易理解整条链：它先让 `ScopePolicyRegistry.resolve()` 精确解析 scope，再让 `QueryPlanCompiler.compile()` 把语义 Intent 转成无 SPL 的类型化计划，最后由 `QueryPolicyGate.authorize()` 重新核对 Intent、计划和 Policy，产生 `AuthorizedQueryPlan`。

```text
QueryIntent
  → registry.resolve(scope_ref)
  → compiler.compile(intent, policy)
  → gate.authorize(intent, plan, policy)
  → AuthorizedQueryPlan
  → SearchRequest
```

测试要重点看拒绝路径：未知 scope、大小写或空白变体、超出时间窗、危险字面量、伪造 template/operation/source，以及策略失败是否在调用 `LogSearchPort` 之前终止。当前代码到 `AuthorizedQueryPlan` 为止；真实 SPL Renderer 并不存在。

## 五层安全边界

```mermaid
flowchart LR
    I["QueryIntent\n语义目标"] --> R["ScopePolicyRegistry\n精确解析范围"]
    R --> C["QueryPlanCompiler\n类型化计划"]
    C --> G["QueryPolicyGate\n正向授权"]
    G --> A["AuthorizedQueryPlan"]
    A --> P["LogSearchPort"]
```

### 1. `QueryIntent`

状态机和 Reasoner 仍然只表达“为什么查”和“要验证什么”。`goal` 不是查询语言。

### 2. `ScopePolicy`

这是应用启动时加载的受信配置，而不是模型输出。它将精确的 `scope_ref` 映射到：

- 允许的 `(index, sourcetype)` 精确配对；
- 允许的模板和查询操作；
- 最大时间跨度；
- 最大返回行数。

Registry 不进行 trim、大小写归一、通配匹配或默认 fallback。未知 scope 一律拒绝。index 和 sourcetype 在配置构造时使用窄字符集校验，`*`、管道、换行、引号和子搜索都不能成为数据源名称。

### 3. `QueryPlanCompiler`

当前只编译两个正向操作：

| QueryKind | template | operation | 动态内容 |
|---|---|---|---|
| `TRIAGE` | `triage.error_summary.v1` | `ERROR_SUMMARY` | 无，固定粗查 |
| `VERIFY` | `verify.event_sample.v1` | `EVENT_SAMPLE` | 一个受约束的字面搜索目标 |

生成的是 provider-neutral `QueryPlan`，不是 SPL。加入数据源后得到的 `AuthorizedQueryPlan` 更准确地说是 **SPL-free、MCP-transport-neutral、Splunk-domain-aware 的非执行计划**。

Verify 的自然语言目标先转换成窄字符集的 `QueryLiteral`；字段表达式、通配符、括号、布尔操作符、管道、宏、子搜索、引号、转义符和控制字符都会被拒绝。普通文本 `delete failed` 不会因为包含单词 `delete` 被误伤，因为策略不使用危险命令关键词黑名单。

这层字面量约束只是纵深防御，不是 SPL escaping。未来 Renderer 仍必须使用版本化固定模板，把 `QueryLiteral` 专门编码为数据，并对最终查询再次验证 source、时间、limit、宏、子搜索和副作用命令。

### 4. `QueryPolicyGate`

Gate 会再次检查：

- plan 的 kind 和时间范围没有偏离原 Intent；
- template 和 operation 位于 scope allowlist；
- Triage 必须使用完整调查时间窗；
- Verify 必须位于调查时间窗内部；
- 时间跨度和结果 limit 没有超过 ScopePolicy；
- 动态字面量满足结构约束。

策略失败不会静默缩短时间或截断 limit，而是返回固定、脱敏的 `QueryPolicyError`。Executor 将它转换成 `OperationFailed`，所以终态是 `FAILED`，不是 `INCONCLUSIVE`。

### 5. `SearchRequest`

Port 现在只收到：

```text
operation_id + query_id + AuthorizedQueryPlan
```

完整的 `QueryIntent` 对象、未解析的 `scope_ref` 和 raw SPL 都不在 Port 请求接口中。Verify 的目标文字会以已经通过 Gate 的 `QueryLiteral` 存在于授权计划里。

Port 只向 Adapter 提供该授权计划；符合契约的 Adapter 必须只消费其中的模板、受信 source pair、时间范围、limit 和字面参数。Python 类型本身不能阻止错误 Adapter 忽略计划，所以这项约束还需要真实 Renderer 审查、契约测试和最终 SPL 校验。

## 结果侧仍要防守

`SearchResult.result_count` 当前定义为返回给应用的规范化行数，不是 Splunk 的总匹配数。若 Adapter 返回的行数超过授权 limit，Executor 会把它视为 `log_search.protocol_error`。

真实 MCP 契约确认后，如果能提供总命中数，会另加 `total_matches`，不能混用这两个概念。当前 `result_limit` 只约束返回应用的规范化行数，不约束 Splunk 的扫描成本、物理分页或 poll 次数；逻辑查询预算也不能替代未来的 page/poll budget。`truncated=False` 目前只是 Adapter 声明，不能证明结果完整。

当前还对 summary、Fact 数量、单条 Fact 文本和 record reference 设置了长度/数量硬上限，但 **normalized 不等于 sanitized**。在结果 Sanitizer/Redactor、字段分类和原文访问策略落地前，不能把真实生产日志交给外部 LLM。

## 这是不是把 Agent 写死了

没有。当前固定的是本地非执行计划的表达边界，以及未来允许映射为可执行查询的能力词汇；这还不是已经验收的 Splunk 执行边界。调查内容仍然是动态的：

- 模型仍可根据证据动态提出假设和验证目标；
- 状态机仍可动态选择继续验证、换假设或结束；
- 计划只能选择本地 allowlist 中、意图为只读的操作标识。

目标原则类似参数化 SQL：参数可以动态变化，但调用方不能提交任意查询语法。当前只完成了非执行计划这一半；必须等 Renderer 的字面编码和最终查询测试完成后，才能认为真正实现了类似的执行安全。

## 当前还没有实现什么

- 没有 raw SPL renderer；它只能存在于未来 Splunk Adapter 内部，并必须使用固定模板和专用字面量转义；
- 没有确认真实 MCP 的 earliest/latest 参数、分页、总命中数和截断语义；
- 没有调用者身份到 `scope_ref` 的授权检查；本地 ScopePolicy 是资源 allowlist，不是用户/租户权限系统；
- 没有确认 Splunk 服务账号的只读 RBAC；应用护栏不能替代服务端权限；
- 没有 PII 字段清单、脱敏规则、保留期和原文查看权限，这些需要系统负责人和安全负责人提供；
- 没有字段级过滤、trace lookup 和聚合字段 allowlist，它们会随领域配置扩展 QueryPlan 的类型化词汇。

若未来将查询执行拆到另一个进程，禁止直接反序列化网络传入的 `AuthorizedQueryPlan` 后执行；接收端必须携带并复核 policy/template 版本，再重新走授权和 Renderer 校验。

第六课已经定义与执行权限隔离的系统领域知识配置，第七课又实现了受限知识投影和结构化推理边界。更丰富的字段型查询能力仍需单独设计物理字段策略和 Renderer，不会让模型直接生成可执行 SPL。
