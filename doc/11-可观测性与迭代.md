# 第 11 章：安全可观测性、回放与评估反馈

> 本章定义下一步要实现的可观测性契约。当前仓库已有状态、预算、错误码和模型投影版本信息，但还没有生产 TraceEvent、TraceSink、存储、保留策略或回放工具。本文不能被理解为“可观测性已经完成”。

未来采集点应包围已有边界，而不改变控制权：

```text
transition 前后       → phase、command/event kind、decision code
QueryPipeline 前后    → policy 版本与允许/拒绝结果
Port 调用前后         → 耗时、计数、超时/取消、规范化大小
Reasoning Adapter     → stage、repair、finish reason、projection provenance
Runner 终止           → terminal phase、termination reason、预算计数
```

本章展示的 `SafeTraceEvent` 是待实现 Schema，不可直接复制成生产方案；字段允许集合、token 密钥、访问控制和保留期仍需部署环境批准。尤其不能为了“调试方便”记录 Prompt、原始异常、日志摘要或 Evidence/record_ref。

## 决策 Trace，不是思维 Trace

日志诊断 Agent 需要回答两个不同的问题：

1. 系统执行了什么？
2. 程序根据哪一条稳定规则走到了下一状态？

第二个问题里的“为什么”必须是程序可验证的 decision code，例如：

```text
triage.no_data
verification.supported
verification.rehypothesize
budget.query_exhausted
operation.failed
```

它不是让模型输出思维过程，也不是保存隐藏 chain-of-thought。模型的内部推理既不是可靠审计证据，也可能包含敏感信息。我们审计的是输入经过了哪些安全边界、模型提交了哪类结构化结果、程序接受或拒绝了什么，以及状态机最终采用了哪条边。

因此安全 trace 的原则是：

> 记录控制事实、计数、耗时、版本和安全结果；不记录诊断内容本身。

## 威胁模型：这些内容禁止进入 Trace

旧版示例把完整 Working Memory、raw SPL、日志摘要和 Evidence ID 直接写入 JSON 文件。这会把一次诊断复制成第二份缺乏数据源权限保护的敏感数据集。

默认禁止记录：

| 禁止内容 | 原因 | 替代记录 |
|---|---|---|
| 原始用户问题 | 可能包含账号、订单、客户和事故信息 | 输入是否通过、字符数区间 |
| raw SPL、literal term | 会泄露查询内容，也可能含用户数据 | `template_id`、operation、策略 decision code |
| index、sourcetype、物理 source | 暴露内部数据拓扑 | 受控 policy 版本/hash，必要时使用 HMAC scope token |
| 原始日志、Fact statement、Query summary | 直接复制生产数据 | 行数、Fact 数、Evidence 数、`truncated` |
| `record_ref`、signed URL、Splunk sid/job URL | 可能成为绕过授权的访问路径 | 每次 trace 内部的短别名或不可逆 HMAC |
| 原始 Evidence/Hypothesis/Query ID | 当前 ID 可能包含 investigation ID，且可被跨系统关联 | event sequence 或带轮换密钥的关联 token |
| Hypothesis statement、Conclusion summary、recommendation | 可能复述日志和用户敏感内容 | 状态、decision code、数量 |
| 模型完整 input/output、Prompt 正文 | 可能复制所有上下文或攻击载荷 | prompt/schema 版本、字节数、finish reason |
| chain-of-thought、reasoning token 内容 | 不是审计依据，且扩大隐私面 | 接受/拒绝码、结构化 verdict |
| 原始 exception、`repr(error)`、stack locals | 常含 URL、请求体、凭据或日志文本 | allowlist `error_code` + 固定安全消息 |

“禁止进入 trace”也包括日志标签、span attribute 和 metric label。把敏感值从 JSON 删掉，却放进 OpenTelemetry attribute，并没有减少泄露。

未知异常的堆栈如果确实需要用于开发排障，应进入独立、权限更高且经过自动清洗的错误监控域，不与诊断 trace 混存，也不返回给用户。

## 经过本地数据分类后，可以记录什么

安全 trace 可以记录以下结构化元数据：

- `phase_before`、`phase_after`、`command_kind`、Event 类型；
- 状态机产生的稳定 `decision_code`；
- terminal phase、`ConclusionOutcome`、`TerminationReason`；
- 查询 template ID、operation、result limit、返回行数、是否截断；
- 新增 Fact/Evidence/Hypothesis 数量，不记录其文本；
- 查询总预算/验证预算的上限和已使用量；
- operation latency、超时、取消、重试次数；
- reasoning stage、repair attempt、finish reason、输入字符数和输出字节数；
- 应用、状态机、query template、prompt 和 schema 版本；
- knowledge bundle/revision/content hash；
- visibility policy id/revision/hash、projection algorithm version/hash；
- allowlist 中的错误码和已经清洗的固定错误消息；
- trace schema version、事件序号和时间戳。

这些字段也不是跨组织通用的“天然无敏感性”清单。若精确结果数、时间戳或版本标识在当前系统中会泄露业务活动，应进一步分桶、降低精度、令牌化或不记录；最终允许集合必须由部署环境的数据分类策略批准。

`StructuredModelRequest.trace_context` 已经保存了一组本地 provenance：知识 bundle、知识 revision/hash、可见性策略 id/revision/hash、投影算法版本和 projection hash。它明确不能被 provider Adapter 放入模型可见 input、metadata 或工具参数；未来 trace sink 可以在本地权限域中记录这些值。

## 使用严格 Schema，不使用任意 detail 字典

旧版 `TraceEvent(kind: str, detail: dict[str, Any])` 允许任何调用方顺手塞入 `wm`、`spl` 或异常对象，无法做可靠审查。下一步实现应该使用封闭枚举、定长字段和每种事件的校验构造器。

下面是一个设计草案，不是仓库中已经存在的代码：

```python
from dataclasses import dataclass
from datetime import datetime
from enum import StrEnum

from log_agent.domain.models import OperationKind, Phase, TerminationReason


class TraceEventKind(StrEnum):
    RUN_STARTED = "run_started"
    TRANSITION = "transition"
    OPERATION_FINISHED = "operation_finished"
    POLICY_DECISION = "policy_decision"
    REASONING_FINISHED = "reasoning_finished"
    RUN_FINISHED = "run_finished"


@dataclass(frozen=True, slots=True)
class SafeTraceEvent:
    schema_version: int
    trace_id: str
    sequence: int
    occurred_at: datetime
    kind: TraceEventKind

    phase_before: Phase | None = None
    phase_after: Phase | None = None
    command_kind: OperationKind | None = None
    decision_code: str | None = None
    termination_reason: TerminationReason | None = None

    duration_ms: int | None = None
    query_template_id: str | None = None
    result_count: int | None = None
    truncated: bool | None = None
    facts_added: int | None = None
    evidence_added: int | None = None

    budget_issued_total: int | None = None
    budget_issued_verify: int | None = None
    repair_attempt: int | None = None
    finish_reason: str | None = None

    prompt_version: str | None = None
    projection_hash: str | None = None
    error_code: str | None = None
    safe_error_message: str | None = None
```

正式实现时还要为每个 event kind 写字段组合校验和长度上限。例如 `POLICY_DECISION` 不允许携带 `safe_error_message` 之外的自由文本；`query_template_id` 必须通过受信配置 allowlist；`safe_error_message` 必须来自固定消息表，不能直接使用异常原文。

运行级 header 应另外记录：

- 不透明 `trace_id`；
- 由轮换密钥 HMAC 得到的 actor/tenant/scope token（仅确有运营需求时）；
- app build、state-machine 和 trace-schema 版本；
- policy 与 knowledge 发布版本；
- 开始/结束时间、终态和事件总数。

不要把邮箱、用户名、租户名、raw `scope_ref` 当成 metric label。需要关联时使用有过期策略的 pseudonymous token，并限制谁能访问映射关系。

## decision code 应由程序产生

自然语言的“证据看起来足够”无法稳定聚合，也可能由模型控制。建议给状态机转移定义封闭的 code，例如：

| 转移情形 | decision code |
|---|---|
| 接受 `StartRequested` 并发出首条 Triage | `run.started` |
| 还有未执行的 Triage | `triage.next_query` |
| Triage 总结果为零 | `triage.no_data` |
| Triage 有数据，进入生成假设 | `triage.data_found` |
| 未生成假设 | `hypothesis.none` |
| 开始验证下一个 Proposed 假设 | `verification.next_hypothesis` |
| 证据不足，继续同一假设 | `verification.continue` |
| 假设受支持，进入结论 | `verification.supported` |
| 假设被反驳，重新生成假设 | `verification.rehypothesize` |
| 无后续路径，证据不足 | `verification.insufficient_evidence` |
| 查询预算不足，生成非收敛结论 | `budget.query_exhausted` |
| 外部操作失败 | `operation.failed` |
| 用户请求取消 | `run.user_cancelled` |
| 结论通过最终不变量校验 | `conclusion.accepted` |

当前 `Transition` 还没有 `decision_code` 字段。实现时有两个选择：

1. 首选：让状态机在 `Transition` 上显式返回一个封闭的 decision code；
2. 过渡方案：使用一个纯函数根据 before state、Event 和 after state 统一分类，并用全部转移测试锁住映射。

不能在各 Adapter 里自行猜测“为什么转移”，也不能根据模型 confidence 生成 decision code。

## Trace 应在哪里采集

不要在领域 dataclass 里到处 `print()`，也不要让 trace 改变状态机结果。建议使用一个应用层 `TraceSink`，在明确边界采集：

| 采集点 | 记录 | 明确不记录 |
|---|---|---|
| 用户入口 | 接受/拒绝码、请求大小区间、授权策略版本 | question、主体真实标识 |
| Runner / transition 包装层 | phase、Command/Event kind、decision code、budget | WorkingMemory、领域文本 |
| CommandExecutor | capability、duration、timeout/cancel/error code | Command 中的 goal、异常原文 |
| SafeQueryPipeline | template、operation、allow/deny code、limit | sources、literal terms、SPL |
| LogSearch Adapter | backend operation outcome、rows、pages、truncated | rows、record_ref、sid URL |
| StructuredReasoningAdapter | stage、repair、finish reason、大小、provenance hash | model input/output、证据别名映射 |
| 结果呈现器 | terminal status、输出大小、编码结果 | summary/recommendations 正文 |

Trace 写入本身要有资源边界：单次运行最大事件数、单事件最大字节数、队列上限和丢弃计数。普通性能 telemetry 可以 best effort；法规要求的安全审计事件是否必须 fail closed，需要由组织的合规策略明确决定，不能由 Adapter 临时选择。

## 指标：先测可靠性和安全，再谈“回答得好”

从安全 trace 可以直接聚合运行指标：

- `COMPLETED / INCONCLUSIVE / FAILED / CANCELLED` 比例；
- 各 `TerminationReason` 比例；
- 每阶段耗时、端口超时和不可用率；
- 每次调查查询数、验证查询数和预算耗尽率；
- query policy deny、结果截断和分页上限命中率；
- 模型 refusal、invalid output、repair attempt 和 output truncation 率；
- 知识投影实体数、字符数和空投影率；
- Trace 丢弃、序号缺口和 schema 拒绝率。

这些指标不能单独回答“根因是否正确”。质量指标必须与第九章的人工或已知答案标签结合：

- 根因正确率；
- 证据接地率；
- 错误收敛率，即没有足够证据却输出 `COMPLETED`；
- 正确弃权率，即证据不足时是否输出 `INCONCLUSIVE`；
- 安全违规率和敏感数据泄漏率；
- 成本、延迟和质量之间的权衡。

错误收敛通常比多一次 `INCONCLUSIVE` 风险更高，评估门槛应该单独限制它，而不是只看平均分。

## 保留、访问和删除策略

“已经脱敏”不等于可以永久保存。上线前必须为不同数据层分别定义策略：

| 数据层 | 建议用途 | 保留原则 | 访问原则 |
|---|---|---|---|
| 聚合指标 | 容量、SLO、趋势 | 可相对更长，但限制低基数维度 | 运维只读 |
| 单次安全 trace | 故障定位和审计 | 尽量短，按事故/法规批准延长 | 最小权限、按租户隔离、访问留痕 |
| 经批准的回放 fixture | 离线回归 | 版本化保留，定期重新审查 | 评估团队和 CI 服务账号 |
| 原始证据/日志 | 证据查看 | 沿用原系统的数据保留和 RBAC，不复制到 trace | 每次访问重新授权 |
| 异常堆栈 | 开发排障 | 独立短期存储、强清洗 | 限定生产工程角色 |

具体天数不能由本课程替组织决定。至少要明确：

- 数据分类、owner、目的和合法依据；
- 传输/静态加密、密钥轮换和备份删除；
- tenant isolation、RBAC/ABAC、break-glass 流程；
- 谁查看、导出或关联过 trace 的审计日志；
- 用户删除、法律保留和到期清理如何传播到副本；
- 开发、测试和生产环境严格隔离；
- 禁止把生产 trace 下载到个人电脑或提交进 Git。

## “回放”分三个等级

安全 trace 刻意不保存原始内容，所以不能从它恢复完整日志或模型回答。这不是缺陷，而是数据最小化的结果。

### 1. 结构回放

只使用 phase、command/event kind、decision code、budget 和终态，检查：

- 状态顺序是否合法；
- 每条 Command 是否有对应结果；
- 查询预算是否单调且未超限；
- 终止原因是否与终态一致；
- 是否出现事件缺口或重复 sequence。

这种回放能定位控制流问题，但不能重新判断日志语义。

### 2. 确定性测试回放

如果某次线上失败值得进入回归集，应经过人工审批和脱敏，把最小必要事实制作成独立的 Fake fixture，并为它分配版本/hash。测试使用 Fake LogSearch 和脚本化模型响应重放。

Trace 只保存 fixture 或 eval case 的版本引用；不能自动把线上问题、日志或模型输出复制进回归目录。

### 3. 重新查询真实系统

重新调用 Splunk 不是“回放”，而是一次新的受授权调查。它必须使用当前调用者、当前 ScopePolicy、新的预算和新的审计记录；旧 trace 不能充当永久授权凭证。

真实 LLM 也不能保证逐 token 重现。要调查模型回归，应保存 provider/model、prompt/schema 和知识版本，并在批准的脱敏 eval case 上比较结构化结果，而不是依赖 chain-of-thought。

## 从 Trace 到评估反馈的安全闭环

线上信号不能自动修改 Prompt、领域知识或查询模板。安全闭环应该是：

```text
聚合指标或人工报错
→ 受授权人员定位 trace
→ 人工选择最小案例
→ 脱敏、去标识和安全复核
→ 标注 expected outcome / evidence rule
→ 加入版本化 eval set
→ 离线比较质量、安全、成本和延迟
→ 审批知识/Prompt/模板变更
→ 小流量或 shadow 验证
→ 监控回归并决定推广/回滚
```

每个变更必须能追溯到：

- eval case 版本；
- knowledge/policy/prompt/query-template 版本；
- 变更前后指标；
- 审批人和部署批次；
- 回滚条件。

KnownFailure 仍然只是候选知识，Trace 中“经常出现”也不能把它升级成证据。查询命中率低也不代表应该自动删除模板，可能只是样本分布、权限或采集异常。

## 动手练习

### 练习 11.1：Canary 泄漏测试

分别在用户问题、日志行、`record_ref`、查询 literal、模型非法输出和异常消息中放入不同 canary。序列化一次完整 trace，断言所有 canary 都不存在，同时 phase、command、budget、错误码和版本信息仍然完整。

### 练习 11.2：转移覆盖

为状态机每一条合法边定义 decision code。遍历领域测试，断言每次 Transition 恰好产生一个允许的 code；新增状态机边时，如果没有 code，测试必须失败。

### 练习 11.3：受控回放

构造一个只含结构事件的 trace，验证预算、事件序号和终态。然后为一个语义错误另建脱敏 Fake fixture，说明为什么二者不能合并为一个“完整线上 dump”。

### 练习 11.4：访问与保留演练

设计三种角色：普通用户、值班工程师、评估维护者。写出每种角色能看哪些字段、保留多久、如何审批导出，并测试跨租户读取被拒绝且拒绝事件被审计。

### 练习 11.5：反馈门槛

为一次 Prompt 或知识变更定义至少五项门槛：错误收敛率、接地率、正确弃权率、P95 延迟和成本。规定哪一项退化会阻止发布，以及如何回滚。

## 验收矩阵

| 验收项 | 通过条件 |
|---|---|
| 数据最小化 | Trace 中不存在 question、SPL、日志、record_ref、领域文本和模型原文 |
| 无思维链 | 不请求、不存储、不展示 chain-of-thought |
| 可解释控制流 | 每次状态转移有程序生成的稳定 decision code |
| 完整关联 | 事件序号连续，Command/结果/终态可结构化关联 |
| 错误安全 | 只记录 allowlist error code 和固定清洗消息，无异常原文 |
| 资源有界 | 单事件、单运行、队列和 metric cardinality 均有硬上限 |
| 版本可追溯 | app、状态机、知识、策略、投影、Prompt/schema 和模板版本可关联 |
| 权限隔离 | 跨租户访问失败；查看、导出和关联行为有审计 |
| 生命周期 | 到期删除覆盖主存储、索引、备份和派生数据 |
| 回放不提权 | 旧 trace 不能直接触发真实查询，也不能充当授权 |
| 反馈有人审 | 线上信号经审批、脱敏、标注和离线评估后才能进入发布流程 |
| 诚实状态 | 在 TraceSink、治理和回放测试完成前，不声称可观测性已上线 |

## 本章结论

> 好的 Agent trace 是一份最小化的控制审计记录，不是把用户问题、日志、Prompt 和模型推理复制一遍。

它应该让我们回答“程序走了哪条边、用了多少预算、哪个版本作出了结构化结果、为什么终止”，同时让没有原始数据权限的人仍然无法从 trace 还原生产日志。只有这样的可观测性，才适合进入评估和持续迭代闭环。
